### 1.2 The research (cited; the design-determining extracts)

- **NIST SP 800-63B-4 §3.1.1.2** (Password Verifiers): (6) "**SHALL NOT** require subscribers to change passwords periodically. However, verifiers **SHALL** force a change if there is evidence that the authenticator has been compromised"; (5) "**SHALL NOT** impose other composition rules"; on change: "verifiers **SHALL** compare the prospective secret against a blocklist… and **SHALL** provide the reason for rejection"; "SHALL implement a rate-limiting mechanism"; "SHOULD offer an option to display the password." **The app's blocklist duty on password CHANGE is unimplemented (F5).**
- **NIST SP 800-63B-4 §3.1.3** (Out-of-Band): email-delivered OOB secrets are **prohibited as authentication** (vulnerable to interception/rerouting; the carve-out: "Confirmation codes that are sent to validate email addresses or are issued as recovery codes… are not authentication processes and not affected by the above prohibition"). **The app's blocking emailed "final verifier" is an email-OOB AUTHENTICATION step as implemented — in tension with -4 if treated as an authenticator; reclassified as a notification/confirmation-of-record, it falls outside the prohibition.**
- **OWASP Authentication Cheat Sheet — "Change Password Feature"**: the baseline is exactly two things — "The user is authenticated with an active session" + "**Current password verification**" (the public-computer abuse case). No emailed code is required. "Require Re-authentication for Sensitive Features": current credentials before password changes (the CSRF/session-hijack mitigation). "Re-authentication After Risk Events": mechanisms = "**Bound Authenticators** — Require an authenticator already bound to the account, such as the current password or a passkey" + "**Minimize User Friction** — Ensure that re-authentication does not disrupt the user experience unnecessarily." "Consider Strong Transaction Authentication": a second factor for sensitive operations is an APPLICATION CHOICE ("some applications"), not a baseline duty.
- **Synthesis (the design-determining reading):** the security baseline (session + current-password reauth, bound authenticators) is ALREADY met by cycle-31's matrix; the blocking emailed code is an application-added hardening whose security value is NARROW (it stops an attacker who has the current password but not the inbox — the phished-credential class) and whose UX cost triggered this cycle; NIST -4 prohibits email OOB *as authentication*; OWASP prescribes friction minimization. **The emailed step's blocking status is re-examined at P1 against cycle-34's recorded rationale (the no-weakening rule governs — see §4.3).**

## 3. Objective

Rebuild the change-password experience per the researched baseline: ONE coherent, explained flow per account class — **local (never-synced): current password + device credential, no email, exactly as cycle-31 P4 built it, presented in the redesigned language; cloud email/password: current-password reauth + new password in a single progressive form, with the emailed confirmation's BLOCKING status re-ruled at P1 from cycle-34's rationale (notification-reclassify if no covered threat is lost, else keep-blocking with the presentation rebuilt); Google-linked: the Google prompt first, the emailed fallback re-ruled identically.** Every step carries one line of why-copy; a canceled factor prompt offers an inline retry (never a dead-end); the CTA is never keyboard-occluded; the new-password entry gets show/hide and honest per-field errors — and the security posture (cycle-31's matrix + cycle-34's mandatory-change-code and forgot-password flows) is preserved or strengthened, never weakened.
