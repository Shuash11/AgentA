The shipped `libapp.so` carries the P6 copy — the user's screenshot is from this APK.
2. **The engine hard-fails on non-arm64.** The pinned plugin throws `UnsupportedError('…litertlm models require an arm64-v8a Android device…')` (`litert_lm_client.dart:606-611`) → the app's classifier maps it to the generic load-failure class (`gemma_service.dart:252-262` — everything except not-installed lands on `loadFailed`) → the P6 retry screen — and **Retry can never succeed** on those devices (cycle-38's S7 correctly blocks the download gate from re-offering). The product-shape defect: the app offers a 2.59 GB download + infinite Retry on ABIs where the model is IMPOSSIBLE.
3. **The S4 escalation path is DEAD on shipped builds.** `[GemmaService] loadInstalled failed:` and all raw-exception logs are `kDebugMode`-gated → **tree-shaken from release AND profile builds** (byte-scan: 0 hits in the shipped `libapp.so`); the plugin's own logging is equally debug-only (`edge_ai_log.dart:26-30`); the LiteRT-LM stderr capture is debug-only (`litert_lm_client.dart:644-646`). `adb logcat -s flutter` on installed v1.8.0 says NOTHING. Cycle-38's S4 determination path (read the raw exception from device logs) is **unreachable in the field**.
4. **Alternative failure causes (same screen, distinguishable by class):** corrupt/truncated `.litertlm` (engine-create null → loadFailed) or S5 OOM (<4 GB phone). The P6 DAO error row exists (`setModelError`, `offline_model_dao.dart:47-61`) — a persisted failure CLASS makes these distinguishable in the field without any log access.
5. **The working tree carries cycle-39's uncommitted P2 work** (6 files: ai_model/online_ai_service/openrouter_service/ai_service + openrouter-side tests) — cycle-39 is paused on the user's key. **Cycle-40's surface is DISJOINT from cycle-39 P2's** (gemma/offline/DAO/gate/chat/picker files) — verified by file list at delegation time; each cycle's commits stage only its own paths.

## 3. Objective

Make the offline-AI surface honest on EVERY device: a device where the model cannot run (non-arm64) never sees the download offer or a retry that cannot succeed — it sees one clear incompatible-device message; a device where the model CAN run gets the P6 recovery path; and every load failure persists a release-visible failure CLASS (the DAO's existing error path) that distinguishes unsupported-ABI / not-installed / engine-init / file / unknown — making cycle-38's S4 (and S5) determination reachable in the field for the first time.

3. **F2/F4 fix = a persisted failure CLASS.** `_classifyLoadError` is extended to return a class alongside the friendly copy — enum: `unsupportedAbi` (the deterministic `UnsupportedError` message), `notInstalled`, `engineInit`, `file`, `unknown` — persisted through the DAO's existing error path (the `setModelError` message carries the class or the setter gains an optional parameter — **verify the signature at implementation; extend only if needed, S2**). The raw exception stays debug-only (the existing rule — no raw text becomes user-facing or release-logged).
4. **The user's ABI fact refines the diagnosis, not the fix** — the gate + class layer are correct in both worlds. The model-file existence check is NOT asked (release builds are not debuggable — `run-as` unavailable; if arm64 + persistent failure is later confirmed, a debug install supplies the raw evidence for the S4 ladder).
5. **S4 disposition (cycle-38): remains OPEN, nothing in the fallback ladder fires yet.** If the ABI fact says non-arm64 → this was the device-compat defect all along (this cycle resolves the user's experience); if arm64 AND the failure persists on the fixed build → engine-native S4 → cycle-38 §4.1 ladder re-ruling (E4B / GPU variant / Qwen .task) BEFORE any model-swap code moves.
