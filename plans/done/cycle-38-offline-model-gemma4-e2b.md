### 1.4 RAM ≤ 6 GB cap — SATISFIED, with measured figures

The pinned plugin's Memory Diagnostics docs (fluttergemma.dev/docs/diagnostics) carry first-hand Android measurements of Gemma 4 E2B (vivo 1933, Android 11): LiteRT-LM **mmaps** the `.litertlm` file, so the RAM cost is the mapped-weights working set plus anonymous heap/KV — not the 2.59 GB file size:

| Backend | `fileBackedBytes` before load | after load | after one prompt |
|---|---|---|---|
| CPU (app's choice) | 103.6 MiB | **800.5 MiB** | **1043.2 MiB** |
| GPU | 102.3 MiB | 1390.3 MiB | 1413.2 MiB |

Resident working set ≈ 0.8–1.05 GB on CPU (reclaimable file-backed pages) plus anonymous heap/KV/activations on top → realistic total process footprint **≈ 1.5–2.5 GB on device — far under the 6 GB cap**. (Caveat recorded in the docs: `fileBackedBytes` counts shared clean pages in full and GPU driver buffers land there on Adreno; treat the deltas, not absolutes, as the model's cost.) Minimum device posture: comfortable on ≥ 4 GB-RAM phones; the user's ≤ 6 GB RAM-usage cap holds with wide margin.

## 3. Objective

Replace the on-device Gemma 3 1B (0.5 GB, text-only, the user's "super dumb") with **Gemma 4 E2B** (2.59 GB native bundle, next-gen, multilingual, function-calling-capable) served by the **LiteRT-LM engine** (`flutter_edge_ai_litertlm` 1.8.6, the release that pairs with the app's pinned core 1.11.4), keeping the app's CPU backend, its download-gate/foreground-service machinery, and its cloud models untouched. The swap reuses cycle-36's migration machinery (marker → uninstall old → re-download), gets the honest download UX its 5× larger asset demands (§2/F2), and never exceeds the user's binding cap: **runtime RAM ≤ 6 GB — measured at ≈ 1.5–2.5 GB total process footprint (§1.4)**.
